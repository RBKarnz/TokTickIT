# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal
Deliver a functional, responsive Requester-facing ticketing experience that allows users to create IT support tickets, manage attachments, and track their own tickets via a temporary Development Requester identity, establishing a reusable UI foundation (Zen Green Theme) and full-stack architecture.

## 2. Stakeholder Request Interpretation
The IT department needs the first version of the ticketing system for end-users (Requesters). Users must be able to submit tickets with a category, related system, priority, summary, description, and supporting attachments. They also need a dashboard ("My Tickets") to view, search, filter, sort, and paginate their tickets, as well as a detailed view for each ticket where they can manage attachments. Since authentication is not yet available, a temporary user selection mechanism ("Development Requester") will be used to simulate different users and enforce data ownership.

## 3. Scope
### Included
- Temporary Development Requester Selection screen and context management.
- Create Ticket form with validation and attachment upload (up to 5 files, max 5MB each, allowed types: JPG, PNG, WEBP, PDF).
- "My Tickets" paginated list with search, filtering, and sorting capabilities.
- Requester Ticket Detail screen (read-only ticket data) with attachment management (download and soft-remove).
- Enforcement of Requester ownership (users can only see and access their own tickets and attachments).
- Database schema updates for Ticket, Attachment, Category, Related System, and RequesterUser.
- Seed data for categories, related systems, and requesters.
- Reusable Zen Green Theme UI components.

### Excluded
- Real authentication, login, logout, passwords, and sessions.
- IT Staff workflow (dashboard, queue, claiming tickets, changing status).
- Ticket collaboration (Public Comments, Internal Notes, Actions Taken).
- Ticket lifecycle beyond creation (resolution, closing, reopening).
- Administration functions for users and reference data.

## 4. Functional Requirements
- FR-01: The system shall provide a screen to select a Development Requester to simulate a logged-in user.
- FR-02: The system shall allow the selected Requester to create a new ticket with required fields and up to 5 attachments.
- FR-03: The system shall display a list of tickets owned by the selected Requester in a "My Tickets" screen.
- FR-04: The system shall allow the Requester to search, filter, sort, and paginate their ticket list.
- FR-05: The system shall provide a Ticket Detail screen showing read-only ticket information.
- FR-06: The system shall allow the Requester to download their active attachments from the Ticket Detail screen.
- FR-07: The system shall allow the Requester to soft-remove their attachments, requiring a removal reason.
- FR-08: The system shall prevent a Requester from viewing or accessing tickets and attachments belonging to another Requester.

## 5. Business Rules
- BR-01: The official Ticket Number is generated by the backend and must be unique (e.g., TKT-YYYY-XXXXXX).
- BR-02: A new Ticket begins with Current Status "New".
- BR-03: Lab 2 uses a Development Requester selector instead of login. The selected identity is for testing only and is not authentication.
- BR-04: Ticket attachments are limited to JPG, PNG, WEBP, and PDF formats, with a maximum size of 5 MB per file.
- BR-05: A maximum of 5 active attachments are permitted per Ticket.
- BR-06: Attachment removal is implemented as a soft removal; the file metadata remains in the database, but the file cannot be downloaded or previewed.
- BR-07: Required fields for ticket creation: Requester, Category, Related System, Requested Priority, Summary, Description.
- BR-08: Ticket Summary must be between 5 and 100 characters.
- BR-09: Ticket Description must be at least 10 characters.
- BR-10: Inactive requesters must not be shown in the Development Requester selection list.
- BR-11: If no Development Requester is selected, the user must be redirected to the selection screen when attempting to access ticketing pages.
- BR-12: If ticket creation succeeds but the attachment upload fails, the system must NOT rollback the ticket creation. It should save the ticket, present a warning to the user about the failed upload, and allow them to retry uploading from the Ticket Detail screen.

## 6. UI Specification Summary
- **Theme:** Zen Green Theme (Primary: #006B3C, Secondary: #0B7A46, Background: #F5F7F6).
- **Responsiveness:** Multi-column on desktop (≥ 992px), two-column on tablet (768-991px), stacked vertically on mobile (< 768px).
- **Controls:** Required fields marked with a red asterisk. Buttons include visible text. Disabled controls are visually distinct.
- **Feedback:** Validation messages appear near the associated field. Loading states, empty states, and error states must be clearly presented.
- **Reference:** Detailed UI specifications are documented in `docs/lab-02/ui-spec.md`.

## 7. Data Changes
- **RequesterUser (New):** id, name, email, isActive, createdAt.
- **Ticket (New):** id, ticketNumber (unique), requesterId (FK), categoryId (FK), relatedSystemId (FK), requestedPriority (Enum), itPriority (Enum, default: 'UNASSIGNED'), currentStatus (Enum), summary, description, createdAt, updatedAt.
- **Attachment (New):** id, ticketId (FK), originalFilename, storedFilename, fileType, fileSize, uploadedAt, isRemoved, removalReason, removedAt.
- **Category (New):** id, name, isActive.
- **RelatedSystem (New):** id, name, isActive.
- **Enums:** Priority (UNASSIGNED, LOW, MEDIUM, HIGH, CRITICAL), TicketStatus (NEW, OPEN, IN_PROGRESS, RESOLVED, CLOSED).

## 8. API Contract
- `GET /api/requesters`: Retrieve active Development Requesters.
- `GET /api/categories`: Retrieve active Categories.
- `GET /api/systems`: Retrieve active Related Systems.
- `POST /api/tickets`: Create a Ticket (Validates input, limits attachments, generates Ticket Number).
- `GET /api/tickets`: Retrieve paginated Tickets for the selected Requester (Supports search, filter, sort).
- `GET /api/tickets/:id`: Retrieve details of one owned Ticket.
- `POST /api/tickets/:id/attachments`: Upload an Attachment to an existing Ticket.
- `GET /api/attachments/:id/download`: Download an active Attachment (Verifies ownership and soft-remove status).
- `DELETE /api/attachments/:id`: Soft-remove an Attachment (Requires removal reason).

## 9. Acceptance Criteria
- AC-01: Given valid Ticket data, when the Requester submits the form, then one Ticket is saved and the official Ticket Number is displayed.
- AC-02: Given no Development Requester is selected, when the user attempts to open My Tickets, then the Requester Selection screen is shown.
- AC-03: Given Requester B is selected, when a Ticket belonging to Requester A is requested, then the Ticket data is not returned (403 or 404).
- AC-04: Given an attachment exceeding 5MB, when the user attempts to upload it, then the upload is rejected with a validation error.
- AC-05: Given an active attachment, when the Requester soft-removes it with a reason, then the attachment is marked as removed and can no longer be downloaded.
- AC-06: Given the My Tickets screen, when the user enters a search term, then only tickets matching the term in the Summary or Ticket Number are displayed.
- AC-07: Given the Create Ticket screen, when the user submits without a required field, then a field-level validation message is shown and the API is not called.

## 10. Definition of Done
- All functional requirements and business rules are implemented.
- All Acceptance Criteria are met and linked to test evidence.
- Unit, API, UI, and E2E tests are implemented, pass locally, and run on the `main` branch.
- UI conforms to the Zen Green Theme and responsive behavior specifications.
- Database migrations are created and seed data is idempotent.
- Code is peer-reviewed via Pull Request into `lab2-staging`.
- README is updated with current setup and test instructions.
- Visual inspection checklist is completed with screenshots.

## 11. Assumptions and Decisions
- **Decision:** Soft-removed attachments will remain in the cloud/local storage temporarily for audit purposes but will be restricted at the API level.
- **Decision:** The Ticket Number format will be `TKT-YYYY-XXXXXX` where `XXXXXX` is a sequential or random unique string.
- **Decision:** Search in My Tickets will perform a case-insensitive partial match on `ticketNumber` and `summary`.

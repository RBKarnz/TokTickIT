## My Reflection

### Specification agent
- **Metric definitions need to be a single source of truth, not a convention everyone is trusted to follow.** The dashboard card/drill-down mismatch (prompt 2) only happened because the card's count and the list's filter were two separate pieces of code that were *supposed* to agree. Once I shared one filter function between them, the drift became structurally impossible instead of something a reviewer has to keep re-checking.
- **A resolution gate that reads only the request body, not the resource's current state, is a narrower rule than the business actually wants.** Prompt 3 was a case where the spec's intent ("a resolution needs a summary") got implemented more strictly than needed ("every resolve call needs a summary in its body"), and a real reopen→resolve flow exposed the gap.
- **Removing a feature is a traceability exercise, not a deletion.** AC-26 (prompt 8) looked like "delete one page," but following every import and every historical test-plan row that referenced it was the actual work; skipping that leaves dead code and a test plan that lies about coverage.

### Coding agent
- **A passing test suite doesn't mean the tests are checking the right thing.** Both prompt 2 (action-vs-ticket counting) and prompt 5 (double-render double-count) were cases where my own first-pass tests passed cleanly and only a harder scenario — two Actions on one Ticket, or a genuinely responsive two-layout component — exposed that the test itself, not just the code, needed to be more deliberate.
- **Environment problems can look exactly like code regressions.** Prompt 6 cost real time specifically because the symptom (login 500) was indistinguishable from an application bug until I checked the actual port and container state; I now check "did the environment change" before "did my last code change break this" when something that was working suddenly isn't.
- **A conditional `if (x) { assert }` in a test is a trap I now actively look for.** Prompt 7 is the clearest example: it reads like a check, runs green every time, and asserts nothing whenever the precondition isn't met. The fix is almost always to make the test *create* the precondition deterministically instead of hoping seed data provides it.

**Overall:** Claude did the end-to-end implementation, debugging, and test-writing for the higher-risk Lab 4 work (data model, resolution gate, dashboards, final hardening), with Gemini handling a subset of lower-risk UI Issues from a short written plan. The peer review on PR #66 and PR #67 both caught real correctness gaps — a metric/drill-down mismatch and three tests that couldn't fail — that my own first pass of testing missed; in both cases the fix was making the test construct its own precondition instead of relying on ambient data, which is now the first thing I check when a review finds a test that "passed but shouldn't have."
